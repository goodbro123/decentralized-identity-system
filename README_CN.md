# 去中心化身份认证系统

一个面向**不可信链下存储环境**设计的、基于区块链的去中心化身份认证系统。

系统将完整 DID 文档存储在链下，同时将关键状态摘要锚定到区块链。通过文档哈希、默克尔树、版本哈希链校验、属性级证明和数据恢复机制，系统能够检测并处理 DID 文档篡改、版本回滚和数据删除等问题。

> 本项目来源于我的本科毕业设计，研究方向为去中心化身份认证与基于区块链的数据完整性保护。

---

## 项目概述

传统去中心化身份系统通常不会把完整 DID 文档直接存储到区块链中，因为链上存储成本较高，同时可能带来隐私方面的问题。

因此，很多系统会选择：

> 链上保存关键状态，链下保存完整 DID 文档。

但这样又会产生一个新的问题：

> **如果链下存储环境本身不可信，DID 文档还能被信任吗？**

链下数据库或第三方存储服务可能出现：

- DID 文档被恶意修改；
- 最新版本被替换为旧版本；
- 身份文档被删除；
- 返回错误或不一致的身份信息。

本项目通过将**可信状态验证**与**链下数据存储**分离来解决上述问题。

区块链负责保存紧凑的 DID 状态摘要，MongoDB 负责保存完整 DID 文档以及相关链下数据。

当系统读取 DID 文档时，后端会重新计算文档对应的密码学状态，并与区块链中的可信状态进行比对，从而判断链下数据是否仍然可信。

## 核心功能

### DID 生命周期管理

系统实现了去中心化身份管理中的主要业务流程：

```text
注册 → 查询 → 更新 → 验证 → 属性证明 → 数据恢复

用户可以完成：

- 创建新的 DID；
- 查询 DID 最新状态；
- 更新 DID 文档；
- 验证 DID 文档完整性；
- 对单个属性生成默克尔证明；
- 恢复损坏或丢失的 DID 文档。

### 区块链状态锚定

系统不会把完整 DID 文档直接写入区块链，而是只保存必要的密码学状态信息。

链上主要记录：

```text
DID
 │
 ├── 版本号 Version
 ├── 文档哈希 Document Hash
 ├── 默克尔根 Merkle Root
 └── 版本哈希 Version Hash
```

这种设计能够降低链上存储开销，同时保留用于完整性验证的可信参考。

### DID 文档完整性验证

系统会对链下 DID 文档重新计算密码学摘要，并与区块链中的可信状态进行比较。

```text
链下 DID 文档
      │
      ▼
   哈希计算
      │
      ▼
区块链可信状态
      │
      ▼
 一致 / 不一致
```

如果结果不一致，系统可以判断链下文档可能发生了未经授权的修改。

### 版本回滚检测

每次 DID 更新都会形成新的版本状态。

系统不仅检查文档当前内容，还会检查版本之间的连续关系，从而发现：

> 最新 DID 文档被替换为旧版本，但旧版本本身内容仍然合法

这一类传统单一文档哈希难以识别的回滚问题。

### 属性级默克尔证明

系统支持基于 Merkle Tree 的属性级验证。

验证方无需获取完整 DID 文档，即可验证其中某一个指定字段是否真实存在于该版本 DID 文档中。

例如：

```text
DID Document
├── publicKey
├── controller
├── organization   ← 需要验证的属性
└── service
        │
        ▼
    Merkle Proof
        │
        ▼
    Merkle Root
        │
        ▼
区块链可信锚点
```

这种方式可以减少不必要的数据暴露，并为选择性披露提供基础。

### DID 数据恢复

系统针对链下 DID 数据损坏或删除的情况设计了恢复机制。

目前支持：

- 多副本恢复；
- 基于 XOR 的纠删码恢复；
- 恢复块重建。

恢复后的数据不会被系统直接信任。

系统会重新计算：

```text
Document Hash
Merkle Root
Version Hash
```

并将结果与：

```text
恢复块中的摘要
+
区块链中的可信状态
```

进行校验。

流程如下：

```text
DID 文档损坏 / 丢失
        │
        ▼
      数据恢复
        │
        ▼
   重建 DID 文档
        │
        ▼
哈希 / Merkle 校验
        │
        ▼
与区块链状态比较
        │
    ┌───┴───┐
    │       │
   合法    非法
    │       │
    ▼       ▼
 写回数据库  拒绝恢复
```

因此，本系统不仅关注“是否能够恢复”，还关注：

> **恢复出来的数据是否可信。**

## 安全模型

本项目假设：

> **链下存储环境可能不可信。**

系统主要考虑以下风险：

| 风险             | 防护机制            |
| ---------------- | ------------------- |
| DID 文档被篡改   | 文档哈希校验        |
| 属性值被修改     | Merkle Root 校验    |
| 历史版本回滚     | 版本状态校验        |
| DID 文档被删除   | 数据恢复机制        |
| 恢复数据遭到破坏 | 恢复后完整性验证    |
| 数据库状态不可信 | 区块链状态锚定      |
| 暴露过多身份属性 | 属性级 Merkle Proof |

因此，区块链在本项目中的作用并不是承担主要数据存储，而是作为：

> **可信状态锚点（Trust Anchor）**

## DID 操作流程

典型 DID 操作流程如下：

```text
1. 用户提交 DID 操作
             │
             ▼
2. Flask 后端校验请求
             │
             ▼
3. 生成密码学状态
             │
       ┌─────┴─────┐
       ▼           ▼
4. MongoDB      5. Blockchain
保存完整文档       保存可信摘要
       │           │
       └─────┬─────┘
             ▼
6. 一致性 / 完整性验证
             │
             ▼
7. 返回结果给前端
```

在验证过程中，后端会根据链下 DID 文档重新构建预期密码学状态，并与链上状态进行比较。

## 研究动机

很多区块链身份研究主要讨论：

> 如何利用区块链建立去中心化信任？

本项目进一步关注一个更加具体的问题：

> **如果 DID 文档存储在一个不可信的链下环境中，去中心化身份还能保持可信性吗？**

本项目不会默认 MongoDB 或其他链下存储服务始终返回正确数据，而是将链下数据视为需要独立验证的对象。

区块链提供不可随意修改的可信参考状态，而密码学结构则将链上的可信状态与链下的大规模 DID 文档连接起来。

整个架构主要尝试在以下方面取得平衡：

- 链上存储成本；
- 数据完整性；
- 数据可恢复性；
- 隐私保护；
- 验证效率。
